Admin audit log

The proposal says Admin can view audit logs. There is no audit table. WP 2.4.

Encrypted email can't be looked up

AES-GCM with a random IV gives different ciphertext each time, so uniqueness checks fail. Add an HMAC “blind index” column. WP 1.3, 1.4.

Reactions can be spammed

Reactions are bare counters. Add an HMAC reaction tag so each user reacts once per cup without storing who. WP 1.3, 3.2.

Demo accounts have no passwords

Seed users need passwords for the demo. They come from a DEMO_PASSWORD env var, never the repo. WP 2.1.

Rules

Four sets. The privacy rules are copied from CLAUDE.md and are not negotiable. A PR that breaks one does not merge.

A · Privacy & security

  1. No one can unmask a poster, admins included. posts never gets a user_id. Ownership is HMAC-SHA256(PEPPER, user_id:post_id).
  2. Access control lives in the API: requirePerm() on every route. Hiding a button is never the check.
  3. Six roles. No role has an unmask permission, and no route for it exists.
  4. Email, student ID, post content and TOTP secrets are AES-256-GCM encrypted at rest. Keys come from env vars only.
  5. Passwords use bcrypt. MFA uses TOTP (speakeasy + qrcode).
  6. Never log authors, reporter identities, passwords, codes or decrypted data.
  7. Clients only ever see fuzzy time labels, never exact timestamps.
  8. Reports store a hashed reporter tag, never a reporter id.
  9. Secrets only in .env or Vercel env vars. Only synthetic data, never real student data.

B · How we work in git

  1. Pull main, then work on your own branch: habiba, mayan, moaaz.
  2. Only edit the files listed in your work package. Shared files (server/schema.js, server/app.js) need a heads-up in the group chat first.
  3. Open a PR into main. Nobody merges their own PR: Habiba reviews Mayan and Moaaz; Mayan or Moaaz reviews Habiba.
  4. Review within 24 hours. Habiba's work is the critical path, so slow reviews delay everyone.
  5. Every PR description has three lines: what, security reason, how to test.
  6. npm test and scripts/attack.sh pass locally before merging. Vercel's free plan blocks previews of Mayan's and Moaaz's commits, so Habiba merges with “Create a merge commit” only (squash and rebase keep the teammate as author, which Vercel blocks) and checks the production deploy.
  7. One line in BUILD_LOG.md per merged work package. Write “(with Claude)” when AI helped.

C · Everyone understands everything

  1. Explain-back: before a PR merges, its author explains it in two minutes to a teammate who did not build it.
  2. Keep code simple. Comment the security reason wherever it isn't obvious.
  3. 30-minute knowledge swap every week: each person demos what they merged.
  4. If AI wrote a line, you must be able to explain that line. Otherwise rewrite it.
  5. Each of us runs the full demo alone at least once before Week 12.

D · Scope discipline

  1. If it is not in the proposal or the brief, it goes to a “Parking lot” list at the bottom of docs/TASKS.md, not into the code.
  2. Parking-lot items are only picked up after the Phase 5 gate passes.
  3. Cut order if we fall behind by Week 8: stretch work first, then stats page polish, then UI polish. Never cut a brief requirement or the runbook.
  4. Each phase ends with a gate. The next phase's work can start early, but nothing counts as done until its gate passes.

WP 5.1

Runbook

MoaazL·3
  • Roles during an incident: incident lead, fixer, communications.
  • First-hour timeline: T+0–10 confirm and assign roles · T+10–25 contain · T+25–45 fix and verify · T+45–60 communicate and record.
  • Scenario A, misconfigured role: detect with attack.sh or the audit log; contain with a Vercel instant rollback or a revert of permissions.js; revoke that role's sessions; review the audit log for what the role did while over-privileged.
  • Scenario B, leaked MFA secret: revoke the user's sessions, reset their MFA, review the audit log since the suspected leak; if DATA_KEY itself may have leaked, rotate it.
  • Communications: who is told, a message template, and a check of the 72-hour breach notification duty under Egypt's Law 151/2020.
  • Recovery targets (RTO 1 hour; RPO from Neon point-in-time restore) and a post-incident review template.

Open decisions for the team

Agree these at the next meeting, before WP 1.2 and 1.3 are finalised. The recommendation is listed first.

How does someone become a Spiller?

Recommended: everyone signs up as Sipper and an Admin grants Spiller, which matches the proposal's role table. Alternative: every new account is a Spiller, which is simpler but makes the Sipper role nearly unused.

Where does the stats dataset come from?

Recommended: synthetic data only. Collecting faculty, year, gender and age at sign-up just to anonymise them later contradicts data minimisation, and that makes a good viva point.

Photo uploads?

Recommended: no uploads unless the stretch slot opens. Not collecting photos removes the metadata risk entirely, and the threat model says so.

Student email verification?

Recommended: store the student ID and email encrypted, but don't send verification emails. Sending email is out of scope.
